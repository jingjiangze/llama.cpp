# 真页级 KV 实现审计（2026-11-02）

对象：在 llama.cpp（prism 系 Vulkan 分支）上实现 KVMem 那套「设备页池 + 按相关性回迁」。
结论先行：**分三级，L1 便宜但不提速；L2 才是 KVMem 的做法，400–800 行；L3 需要改内核。**

---

## 0. 现状：注意力看到的是什么

关键代码：

| 位置 | 事实 |
|---|---|
| `src/llama-graph.cpp:3260-3265` | `k`/`v` 来自 `inp_attn` 的**整块缓存张量**，再 `ggml_pad` 到 mask 宽度 |
| `src/llama-graph.cpp:3300-3303` | 输入由 `build_input_k_idxs` / `build_input_v_idxs` / `build_attn_inp_kq_mask` 三件组成 |
| `src/llama-kv-cache.h:201-205` | `get_k(ctx, il, n_kv, sinfo)` —— K 视图的尺寸由调用方给，即 **cell 数** |
| `src/llama-kv-cache.cpp:593-615` | mask 按每个 cell 的 `seq_has` 与 `pos` 生成：**没被占用的 cell 自然被 mask 掉** |

也就是说：**「哪些 cell 参与注意力」这件事，现有 mask 机制已经支持了（稀疏驻留本来就合法）**。
真正的成本在别处 —— attention 读的是**整块 K 张量**，张量尺寸 = 已分配 cell 数。
所以：

> **只要设备上的 cell 少了，就一定快；只改 mask 让某些 cell 不参与，一点都不会快。**

这条是理解整个方案的分水岭。

## 1. 三级阶梯

### L1 — mask 级"页选择"（不省带宽）

**做法**：在 mask 生成处（`llama-kv-cache.cpp:593-615`）加一个「选中页集合」，非选中 cell 置 `-inf`。

- 改动：约 **80–150 行**（新增 page-set 传参 + mask 过滤 + 一处 env/参数开关）
- 风险：低（不动内存布局、不动内核）
- **收益：0 性能**。K 张量还是那么大，attention 该读的字节一个不少
- 用途：只用来**验证「选页后答案还对不对」**，是 L2 的正确性前置

### L2 — 驻留窗口 + 主机页存储（KVMem 的做法）★

**做法**：设备侧 KV 只分配 P 个 cell（P = 窗口 token 数，例如 12,800）；
其余页的 KV 字节放主机内存；每步按需把选中页 H2D 灌进空闲 cell。
因为 K 张量只覆盖 P 个 cell，**注意力成本 ∝ P**，所以真的快、真的能开大逻辑上下文。

需要动的东西：

| # | 内容 | 位置 | 估计 |
|---|---|---|---|
| 1 | 新内存实现（或现有类的 paged 模式） | 实现 `src/llama-memory.h:83-126` 的 `llama_memory_i` 接口 | 120–200 行 |
| 2 | cell 逐出/回填 | KV 字节读写：`get_k/get_v` 取张量 + backend buffer 偏移；位置映射插入 | 150–300 行 |
| 3 | 选页策略 | 四桶预算（protect/skeleton/evidence/recent/free）或 LRU+相关性 | 80–150 行 |
| 4 | 上下文/参数接线 | `llama-cparams.h` 加开关，`llama-context.cpp` 构造分支 | 40–80 行 |
| 5 | 页存储 | 主机侧按 (seq, pos 块) 存字节；可复用 `state_write/state_read` 的序列化思路 | 60–120 行 |

**合计 450–850 行**，不需要改内核（这是它比 L3 划算的地方）。

**真正的难点（按风险排序）**：

1. **pos→cell 映射的插入语义**：现有只有 `seq_add`（整体 shift），没有「把任意 pos 塞进指定 cell」。
   而 paged 需要「恢复一页时，把这批 pos 重新挂到空闲 cell 上」—— 要新写插入路径，并保证 `seq_pos_min/max`、defrag 一致。
2. **与其他序列共存**：llama.cpp 的 cell 有 per-seq pos 集合，逐出某序列的页时不能碰别人的 cell。
3. **defrag**：现有 defrag 假设缓存归自己管；paged 模式下必须禁用它或让它理解"空页"。
4. **MTP 草稿上下文**：它是独立 cache（`cparams.ctx_type = LLAMA_CONTEXT_TYPE_MTP`），要么同步分页，要么整体驻留（草稿注意力本来就短）。
5. **正确性判据**：页缺失时静默降级**不报错**是最危险的失败模式（KVMem 自己也承认 80K/128K 召回只有 1/3）。

### L3 — 非连续 KV 视图 + 分段内核（省掉 mask 内的读取）

让 attention 只读「页表列出的 cell」，需要 FA kernel 支持间接索引。

- `ggml-vulkan` 的 flash_attn / mul_mat_vec 路径都要改
- 估计 **1000+ 行 + 内核改造**，且必须重跑数值一致性
- 只有 L2 里"P 还是太大"时才有意义

## 2. 为什么现在的 kv-pager 代理到不了 L2

它是 **L0（前缀级）**：

- `slot save/restore` 是**整份 KV dump**（实测 **472 MB / 份**，8K 与 128K ctx 都是这个量级）
- 它保住的是「换问句不用重 prefill」，**不是**「单请求超窗也不丢信息」
- 单请求超窗仍然靠 `compactMessages` 裁剪（丢内容、不是paging）

所以代理和 L2 是两件不同的事，不能混为一谈。

## 3. 如果要真做，建议的切片顺序

1. **L1（1–2 天）**：加 page-set 开关，mask 过滤。验收 = 「只让最近 8K 的 cell 参与注意力，模型答案退化到可预期程度、且不崩」。
   这一步把「选中页」这个动作的正确性先钉死。
2. **L2 的读写原语（2–3 天）**：先只做「逐出一页 → 存主机 → 原样灌回 → 数值逐 token 一致」，
   不做选页策略（固定 LRU）。这是整个方案里最容易出错的一段，必须先证明字节级无损。
3. **L2 的选页策略（1–2 天）**：四桶预算 + 相关性打分。验收用现成的 needle 用例（`ret-8000/16000/32000.json`）。
4. **接 MTP 草稿上下文**（0.5 天）：草稿上下文建议**不分页**（它只读短窗口），避免双份复杂度。
5. **性能验收**：同深度 tg 对比 + 峰值显存。判据：设备池 P 减半时 tg 不掉、显存降 ≥1 GiB、needle 不降。

风险提示：第 2 步失败（字节对不齐、pos 插入破坏 defrag）的概率不低。**不要在没跑通「逐出→灌回→逐 token 一致」之前接任何选页策略。**

## 4. 与「买/换实现」的对比

| 方案 | 工作量 | 能否在 B580 上用 |
|---|---|---|
| KVMem（CUDA） | 0 | ❌ 无 Intel 后端 |
| L1+L2 自研 | 450–850 行 + 5–8 天 | ✅ 但需自己验证 |
| 只留 kv-pager（L0） | 已完成 | ✅ 只能解决"换问句" |

在当前 12 GB / Vulkan 的约束下，**L2 是唯一能同时拿到「长上下文」和「不掉速」的路**，
也是唯一一条没有现成替代品的路。是否投入，取决于「单请求超 64K」这个场景到底有多重要 ——
如果日常是「多轮但每轮不超 64K」，L0 代理就够了；如果真要吃 128K+ 单请求，才需要 L2。
